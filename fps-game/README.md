# Bunker Break

브라우저에서 도는 1인칭 웨이브 서바이벌. 좁은 벙커에 파도처럼 밀려오는 적을
막아내며 몇 번째 웨이브까지 버티는지를 겨룬다. 양옆에 높은 통로가 있어,
계단으로 올라가 내려다보며 싸우거나 다시 내려와 붙을 수 있다.

```bash
npm install
npm run dev
```

모델·텍스처·음원 파일이 하나도 없다. 적도 무기도 맵도 Three.js 기본 도형으로
그 자리에서 만들고, 총소리는 Web Audio 로 합성한다. 받아올 것이 없으니
빌드 결과물만 있으면 어디서든 돈다.

## 조작

| 입력 | 동작 |
|---|---|
| W A S D | 이동 |
| 마우스 | 조준 |
| 좌클릭 | 발사 · 휘두르기 |
| R | 재장전 |
| Shift | 전력 질주 (전진할 때만) |
| Space | 점프 |
| 1 · 2 · 3 | 주무기 · 보조무기 · 근접무기 |

| Esc | 일시정지 |

시작하면 마우스가 화면에 잠긴다. Esc 로 풀면 자동으로 멈춘다.

## 규칙

**무기 아홉 자루가 슬롯 셋**으로 나뉜다. 숫자키가 무기 이름이 아니라 역할을
가리켜서, 무엇을 주웠든 손이 찾는 자리가 바뀌지 않는다. 한 자리를 여럿이
나눠 쓰고, 같은 숫자를 다시 누르면 그 안에서 교대한다 — 새로 주웠다고 쓰던
것을 잃지 않는다.

| | 무기 | 성격 | 얻는 곳 |
|---|---|---|---|
| **1** 주무기 | 돌격소총 | 두루 쓴다 | 2웨이브 |
| | 샷건 | 코앞에서 압도적, 멀면 무의미 | 4웨이브 |
| | 경기관총 | 탄창 100발로 무리를 눕힌다. 대신 정밀함과 4.2초 재장전을 내준다 | 8웨이브 |
| | 대물 저격총 | 한 발이 크고, 줄지어 선 셋까지 **꿰뚫는다** | 10웨이브 |
| **2** 보조 | 권총 | 예비탄 무한. 다 떨어졌을 때 남는 것 | 처음부터 |
| | 기관단총 | 근거리 속사. 조금만 멀어도 힘이 없다 | 3웨이브 |
| | 매그넘 | 여섯 발뿐이지만 한 발이 무겁다 | 6웨이브 |
| **3** 근접 | 전투 나이프 | 빠르다. 크롤러는 한 방 | 처음부터 |
| | 전투 도끼 | 느리고 크게 벤다. 브루트도 두 방 | 5웨이브 |

총은 헤드샷이 두 배. 근접은 헤드샷을 따지지 않는다 — 여럿을 동시에 베는데
누구는 머리고 누구는 몸통이라고 하면 같은 동작의 결과가 설명되지 않는다.

셋만 히트스캔이 아니다.
- **근접** — 광선 하나로는 발밑의 크롤러를 자꾸 놓친다. 사거리·부채꼴·시야를
  만족하는 적을 전부 벤다. 거리는 몸 중심이 아니라 표면까지로 재서,
  브루트가 몸을 맞대고 있으면 실제로 닿는다.
- **관통** — 저격총은 첫 적에서 멈추지 않는다. 가까운 순으로 셋까지 뚫되
  뒤로 갈수록 약해져서, 줄을 세워 쏘는 판단이 값을 하되 무한정 세지지 않는다.

**적 셋**은 실루엣만 보고 구분되게 만들었다. 어두운 방에서 덩치만 보고
"저건 브루트다, 피해야 한다"가 즉시 나와야 한다.

- **크롤러** — 낮고 빠르다. 몰려온다. 눈높이로 쏘면 머리 위로 넘어간다.
- **트루퍼** — 멀리서 쏜다. 벽 뒤에서는 못 쏘고, 못 쏘면 다가온다.
  사거리는 아레나 절반보다 짧아서, 물러나면 벗어날 수 있다.
- **브루트** — 느리고 단단하고, 맞으면 세게 밀린다.

적의 사거리는 높이까지 넣어 잰다. 통로 아래에 선 크롤러가 2미터 위를 무는
일은 없다 — 그러면 높은 자리를 만든 이유가 사라진다.

**높이**가 판을 가른다. 양옆 통로(높이 2)는 계단으로만 오른다 — 바닥에서
점프해서는 닿지 않는다. 올라서면 광장 벽 너머가 보이고, 바닥에 선 적은
손이 닿지 않는다. 다만 안전지대는 아니다: 적도 같은 계단으로 올라온다.
올라간 값은 시야이지 무적이 아니다.

**웨이브**는 번호에 대해 단조증가한다. 개체수는 상한에서 멈추고, 그 뒤로는
체력과 속도에 배율이 붙는다. 속도 배율에는 천장이 있다 — 가장 빠른 적도
플레이어보다 느려야 "물러나며 쏘기"가 계속 통한다.

**체력은 한동안 안 맞으면 서서히 찬다.** 이게 없으면 열 번째 웨이브의
난이도가 열 번째 웨이브의 실력이 아니라 첫 웨이브에서 실수했는지로 정해진다.
교전 중에는 안 차므로, 물러나 숨을 돌릴지가 판단이 된다.

**콤보**는 3초 안에 다음 처치가 이어질 때만 유지된다. 구석에서 한 마리씩
빼는 것보다 붙어서 몰아치는 쪽이 점수가 높다.

## 구조

```
src/
  game/            순수 규칙 — React 도 Three.js 도 모른다
    rng.js           씨앗 받는 난수 · 결정적 해시
    arena.js         맵 — 축에 나란한 상자 목록 · 통로와 계단
    collide.js       원 대 상자 충돌 · 발밑 높이 · 광선 판정 · 시야
    weapons.js       무기 수치
    combat.js        명중·피해·탄퍼짐
    enemies.js       적 수치와 상태 기계
    waveSpawner.js   난이도 곡선 · 스폰 일정
    score.js         점수·콤보·최고 기록
    player.js        이동·점프·사격·재장전
    session.js       위를 묶어 "한 판"을 굴린다
  three/           그리기 — game/ 의 상태를 받아 그리기만 한다
    Arena.jsx        바닥·벽·조명
    Enemy.jsx        절차적 적 모델 세 종
    weaponMaterials.js  강철·폴리머·나무·놋쇠 …
    weaponParts.jsx  총열·탄창·레일·가늠쇠 같은 조각들
    Weapon.jsx       그 조각으로 조립한 무기 아홉 자루 + 총구 화염
    Effects.jsx      예광선·불꽃
    Pickups.jsx      보급품
    PlayerRig.jsx    카메라 ↔ 세션 ↔ 소리를 잇는 곳
  ui/              HUD 와 화면들 (DOM)
  hooks/useInput.js  키·마우스를 "뜻"으로 바꾼다
  audio.js         파일 없이 합성하는 소리
```

`game/` 은 브라우저 없이 그대로 돈다. 이게 이 프로젝트에서 제일 중요한 선이다 —
규칙이 렌더링에 얽혀 있으면 "체력이 0이면 정말 죽는가" 같은 것을 확인하려고
매번 게임을 켜서 손으로 쏴 봐야 한다.

## 테스트

```bash
npm test
```

- `test/logic.test.mjs` — 규칙 검증 **58,000여 개**. 벽 통과·터널링·적 끼임·
  공중 걷기 같은 것을 무작위 대량 시행으로 확인하고, 마지막에는 8웨이브를
  봇으로 끝까지 돌려 값이 깨지지 않는지 본다.
- `test/render.test.jsx` — 렌더링 계층 검증. R3F 테스트 렌더러로 씬을 머리 없이
  세우고 프레임을 돌려, 쏘면 실제로 죽고 그 사실이 UI 로 전달되는지까지 본다.

테스트가 실제로 잡는지도 확인했다. 구현을 **51가지**로 일부러 망가뜨려
(헤드샷 배율, 엄폐물 무력화, 터널링 부활, 적 길찾기 퇴행, 속도 상한 제거,
근접 부채꼴 판정 제거, 칼이 벽을 통과, 관통이 엉뚱한 적을 뚫기, 무기 하나를
영영 못 쥐게 만들기, 공중을 걷게 만들기, 계단을 못 오르게 만들기 등)
**51개 모두** 테스트가 잡아냈다.

안 잡힌 변이가 몇 번 있었는데, 매번 배울 게 있었다.

**한 번은 코드가 문제였다.** 나이프 탄창을 `Infinity` 로 두었더니
`Infinity - 1` 도 `Infinity` 라, "근접무기는 탄약을 안 쓴다"는 방어 코드를
지워도 아무 일이 없었다. 있으나 마나 한 코드였던 것이다. 탄창을 0 으로
바꾸니 그게 없으면 칼이 바로 먹통이 되고, 변이도 잡혔다.

**한 번은 테스트가 문제였다.** 관통 시험에서 적을 가까운 순으로 만들어
넣었더니, "가까운 순으로 정렬" 코드를 통째로 지워도 통과했다. 이미 정렬된
것을 정렬해 봐야 티가 안 난다. 실제 게임의 적 배열은 스폰 순서지 거리
순이 아니므로, 섞어 넣도록 고치니 잡혔다.

**한 번은 시험 자체가 불가능한 상황을 만들고 있었다.** 높이가 생긴 뒤,
"아래에 선 적이 위를 못 때린다"를 확인하려고 적을 계단 한가운데에 y=0 으로
놓았다. 지형 속에 파묻힌 자리라, 밀어내기가 통로 안쪽으로 밀어내며 있을
수 없는 위치에서 때렸다. 게임의 결함이 아니라 시험이 만든 상황이었다 —
진짜 바닥에 세우니 통과했다.

## 기획서와 달라진 곳

`GAME_DESIGN.md` 는 물리 엔진(Rapier)을 쓰겠다고 적었지만 직접 짰다.
필요한 물리가 "벽을 못 지나간다" 하나뿐이고 맵이 전부 축에 나란한 상자라,
원-상자 밀어내기 60줄로 끝났다. 대신 얻은 것이 크다 — 순수 함수라 Node 에서
바로 검증되고, WASM 이 없어 번들과 로딩 실패 경로가 줄었다.

만들면서 기획서가 틀렸던 것도 하나 나왔다. 중앙 엄폐물을 십자로 두었더니
팔 사이 대각선 틈이 0.57 로, 플레이어 지름(0.72)보다 좁았다. 거기 낀 것은
양쪽에서 번갈아 밀려 밀어내기가 수렴하지 못하고 결국 벽을 뚫는다. 눈으로는
"좀 좁은 골목"으로만 보이는 배치가 물리를 깨뜨린 것이라, 지금은 상자 사이
틈이 0이거나 2.0 이상이어야 한다는 규칙을 테스트가 지킨다.
